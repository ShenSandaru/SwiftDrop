## 2. Architecture and module ownership (Existing)

Modular monolith, module list, allowed dependency graph, package rules and table ownership are
decided in [ADR 0003](adr/0003-backend-modules-and-boundaries.md) and enforced by
`ModuleBoundaryTest`. Summary for planning only:

```text
identity → none      pricing → none       delivery → identity, pricing
dispatch → identity, delivery             merchant → identity, delivery
notification → identity, delivery         tracking → delivery
```

- Other modules import only `com.swiftdrop.<module>.api`. `config` is the composition root and
  may use any module's `api`; `shared` holds technical code only.
- Cross-module references are IDs, never JPA associations. Cross-module FKs only where justified;
  no cascading deletes across modules.
- Migrations live in `db/migration/<module>/V<yyyyMMddHHmm>__<module>_<description>.sql`
  (checked by `MigrationConventionTest`). Never edit a merged migration.

## 3. Shared conventions

### 3.1 Identifiers, time, money (Existing unless marked)

| Concern | Rule | Status |
|---|---|---|
| Entity IDs | `UUID` / `uuid`, generated by Hibernate (`GenerationType.UUID`) | Existing (team decision, milestone 2) |
| Reference data | Natural key allowed (e.g. `roles.name`) | Existing |
| Timestamps | `java.time.Instant` / `TIMESTAMPTZ`, stored in UTC; JSON ISO-8601 UTC (`2026-10-25T10:15:30Z`) | Proposed (matches `users.created_at`) |
| Business day | Day boundaries for "deliveries per day" and "deliveries for the day" use `Asia/Colombo` (configurable `SWIFTDROP_BUSINESS_TIME_ZONE`) | Proposed, **D-08**, **D-09** |
| Money | `BigDecimal`, `NUMERIC(12,2)`, rounding `HALF_UP` to 2 decimals at the end of a calculation; currency `LKR` as `CHAR(3)` on every stored amount; JSON as a string `"450.00"` plus `"currency": "LKR"` | Proposed, **D-07** |
| Weight | `int weightGrams` / `INTEGER`, 1–30 000 | Proposed, **D-24** |
| Enums | Java `enum`, stored `VARCHAR(n)` with `@Enumerated(STRING)` and a `CHECK` constraint listing the values; JSON uses the same upper-case names | Proposed (matches `roles`, `external_identities.provider`) |
| Optimistic locking | Mutable aggregates (`parcels`, `merchants`, `pricing_rules`) have `version BIGINT` with `@Version` | Proposed |
| Emails | Trimmed, lower-cased (`User.normalizeEmail`) | Existing |
| Phone numbers | `VARCHAR(20)`, E.164 (`+94771234567`), validated by regex; personal data | Proposed |

### 3.2 Validation (Existing rule, Proposed detail)

- All external input is validated on the backend with Jakarta Bean Validation on request records
  (`@Valid`), plus domain checks in the application layer. Frontend validation is convenience only.
- Request DTOs are Java records in the module's `web` package; no Lombok; unknown JSON fields are
  ignored (they can never set roles, owners or status).
- Free-text limits: names 200, address line 200, notes 500, business name 200.

### 3.3 Error responses (Existing in `identity`, Proposed project-wide — D-15)

RFC 9457 `application/problem+json`, as `IdentityExceptionHandler` already does. Proposed: a single
`shared.web` handler for common cases, modules keep handlers for their own exceptions.

```json
{
  "type": "about:blank",
  "title": "Bad Request",
  "status": 400,
  "detail": "Invalid request",
  "invalidFields": ["dropoff.phone", "weightGrams"]
}
```

| Status | Use |
|---|---|
| 400 | Validation or malformed body; `invalidFields` lists field names, never values |
| 401 | Missing/invalid token or API key (same body for all causes) |
| 403 | Authenticated but wrong role |
| 404 | Not found **or not owned by the caller** (ownership failures never reveal existence) |
| 409 | Conflict: duplicate, illegal status transition, concurrent update (`@Version`) |
| 422 | Not used (keep 400/409 only) |
| 500 | Generic `"Unexpected error"`; stack traces and exception messages never returned or logged with personal data |

### 3.4 Pagination (Proposed — D-15)

Query `?page=0&size=20` (max 100, default 20), optional `sort=createdAt,desc` from an allow-list.
Response:

```json
{ "items": [ ... ], "page": 0, "size": 20, "totalItems": 57, "totalPages": 3 }
```

## 4. API conventions

### 4.1 Existing

- Paths are plural kebab-case nouns under `/api/v1/...`.
- Bearer JWT in the `Authorization` header only; CORS for `SWIFTDROP_CORS_ALLOWED_ORIGINS`
  without credentials; CSRF disabled (stateless).
- Implemented endpoints: `POST /api/v1/users`, `POST /api/v1/auth/tokens`, `GET /api/v1/users/me`,
  `GET /oauth2/authorization/google`, `GET /login/oauth2/code/google`.

### 4.3 Request and response examples (Proposed)

**Price quote** `POST /api/v1/price-quotes`

```json
{ "pickupZoneId": "8f1c…", "dropoffZoneId": "2b7e…", "size": "SMALL", "weightGrams": 2000 }
```

```json
{ "amount": "650.00", "currency": "LKR", "pricingRuleId": "c3d4…",
  "breakdown": { "baseFee": "400.00", "weightFee": "200.00", "sizeSurcharge": "50.00" } }
```

**Create parcel** `POST /api/v1/parcels` (customer). The fee is recalculated by the backend; a
client-supplied fee is ignored.

```json
{
  "pickup":  { "contactName": "Nimal Perera", "phone": "+94771234567", "line1": "12 Temple Rd",
               "line2": null, "city": "Colombo 05", "zoneId": "8f1c…", "postalCode": "00500" },
  "dropoff": { "contactName": "Kumari Silva", "phone": "+94711234567", "line1": "4 Lake View",
               "line2": null, "city": "Kandy", "zoneId": "2b7e…", "postalCode": "20000" },
  "size": "SMALL",
  "weightGrams": 2000,
  "description": "Books"
}
```

`201 Created`, `Location: /api/v1/parcels/{id}`:

```json
{
  "id": "5a0e…", "trackingNumber": "SD7K3M9Q2XWB", "status": "CREATED",
  "fee": { "amount": "650.00", "currency": "LKR" },
  "assignedCourierId": null, "createdAt": "2026-10-25T10:15:30Z"
}
```

**Status change** `POST /api/v1/parcels/{id}/status-changes` (assigned courier)

```json
{ "toStatus": "FAILED", "failureReason": "RECIPIENT_UNAVAILABLE", "note": "Gate locked, 2 calls" }
```

`200` with the parcel detail; `409` with `"detail": "Illegal status transition"` if not allowed.

**Merchant order** `POST /api/v1/merchant-orders`, header `X-Api-Key: sdk_<prefix>_<secret>`
(**D-03**): same body as *Create parcel* plus `"merchantOrderReference": "ORD-10045"`. `201` on
creation; `200` with the existing parcel when the same reference is sent again (**D-25**).

**Public tracking** `GET /api/v1/tracked-parcels/SD7K3M9Q2XWB` (**D-16**)

```json
{ "trackingNumber": "SD7K3M9Q2XWB", "status": "IN_TRANSIT",
  "pickupZone": "Colombo", "dropoffZone": "Kandy",
  "history": [ { "status": "CREATED", "occurredAt": "2026-10-25T10:15:30Z" },
               { "status": "PICKED_UP", "occurredAt": "2026-10-25T12:01:02Z" } ] }
```

**SSE** `GET /api/v1/tracked-parcels/{n}/events`, `text/event-stream`: first event `snapshot`
(the public tracking body), then `status` events
`{"status":"OUT_FOR_DELIVERY","occurredAt":"…","sequence":4}`; heartbeat comment every 25 s.

**Webhook** (Existing, ADR 0004 §2 and §7.2): body = `parcel.status-changed` envelope;
headers `X-SwiftDrop-Event-Id`, `X-SwiftDrop-Event-Type`, `X-SwiftDrop-Timestamp`,
`X-SwiftDrop-Signature: v1=<hex HMAC-SHA256 of "<timestamp>.<raw body>">`.

```json
{
  "eventId": "0f4b…", "eventType": "parcel.status-changed", "schemaVersion": 1,
  "occurredAt": "2026-10-25T12:01:02Z", "producer": "delivery",
  "data": { "parcelId": "5a0e…", "trackingNumber": "SD7K3M9Q2XWB",
            "previousStatus": "CREATED", "newStatus": "PICKED_UP", "sequence": 2,
            "source": "MERCHANT", "ownerCustomerId": null, "ownerMerchantId": "77aa…",
            "merchantOrderReference": "ORD-10045", "failureReasonCode": null }
}
```

columns are plain UUIDs; "FK" means a database foreign key. PII = personal data (never logged,
never in events).

## 6. Authentication, roles and ownership

**Existing:** roles `CUSTOMER`, `MERCHANT`, `COURIER`, `DISPATCHER_ADMIN` (one combined
Dispatcher/Admin role); JWT `sub` = user ID, `roles` claim → `ROLE_<name>`; `@PreAuthorize`
enabled; public registration and Google sign-in grant only `CUSTOMER`.

**Proposed:**

- Staff accounts (**D-04**): the first `DISPATCHER_ADMIN` is created at startup from
  `SWIFTDROP_BOOTSTRAP_ADMIN_EMAIL` / `SWIFTDROP_BOOTSTRAP_ADMIN_PASSWORD` if no admin exists;
  admins create `COURIER` and further `DISPATCHER_ADMIN` accounts.
- Merchant users (**D-22**): registration creates a user with role `MERCHANT` and a `PENDING`
  merchant. Merchant capabilities additionally require merchant status `APPROVED`, checked by the
  `merchant` module on every request (role alone is not enough).
- Merchant API (**D-03**): API key in `X-Api-Key`, format `sdk_<12-char prefix>_<32-byte base64url secret>`;
  lookup by prefix, constant-time hash comparison (SHA-256 is acceptable because the secret is
  high-entropy; BCrypt not needed); authenticated principal carries `merchantId` only, never a
  user role. Requests from a non-approved merchant → 401.

**Ownership rules (Proposed; each needs a test, TST-2):**

| Resource | Customer | Merchant | Courier | Dispatcher/Admin | Public |
|---|---|---|---|---|---|
| Parcel detail / history | own (`customer_id`) | own via dashboard (`merchant_id`) | currently assigned only | all | — |

## 7. Parcel lifecycle

**Existing (ADR 0003 §4):** statuses `CREATED → PICKED_UP → IN_TRANSIT → OUT_FOR_DELIVERY →
DELIVERED / FAILED`; forward one step; `DELIVERED`, `FAILED` terminal; only the assigned courier
makes ordinary updates; a courier must be assigned before `PICKED_UP`; each change records time
and actor; `FAILED` requires a reason. `delivery` alone changes status; sequence per parcel,
`CREATED` = 1 (ADR 0004 §4.1).

**Proposed (D-06):**

| From | Allowed to | Who | Extra rules |
|---|---|---|---|
| `CREATED` | `PICKED_UP` | assigned courier | courier assigned |
| `PICKED_UP` | `IN_TRANSIT`, `FAILED` | assigned courier | `FAILED` needs reason code |
| `IN_TRANSIT` | `OUT_FOR_DELIVERY`, `FAILED` | assigned courier | |
| `OUT_FOR_DELIVERY` | `DELIVERED`, `FAILED` | assigned courier | `DELIVERED` needs proof with recipient name (photo optional) |
| `DELIVERED`, `FAILED` | — | — | terminal; no retry, no cancellation in v1 |

- Assignment / reassignment by Dispatcher/Admin only while status is `CREATED`.
- No admin status override and no cancellation in v1.
- Failure reason codes (**D-19**): `RECIPIENT_UNAVAILABLE`, `ADDRESS_NOT_FOUND`, `REFUSED`,
  `DAMAGED`, `OTHER`. The free-text note stays in `delivery` and never leaves it in events.
- Every change: lock the parcel (`@Version` or `SELECT … FOR UPDATE`), increment `last_sequence`,
  write history + outbox row in one transaction, then publish an in-process after-commit event
  for `tracking`.

### 8.2 Pricing

Customer gets a quote (`/price-quotes`) before confirming; `delivery` calls `FeeCalculator` again at
creation and stores the fee snapshot (`fee_amount`, `pricing_rule_id`). Later rule changes never
change existing parcels.

### 8.3 Merchant order intake

`merchant` authenticates the key, checks `APPROVED`, validates the body and calls
`ParcelCreation.create` with `source = MERCHANT`. Duplicate `merchantOrderReference` for the same
merchant returns the existing parcel (`200`) without a second event (**D-25**).

### 8.4 Dispatch

`dispatch` lists `ParcelQueries.unassigned`, checks courier eligibility, calls
`ParcelAssignment.assign`; `delivery` enforces "status is `CREATED`" and records it. Workload =
`activeCountsByCourier` (non-terminal parcels assigned), joined with dispatch's courier list.

### 8.5 Events, notifications, webhooks (Existing — ADR 0004, not repeated here)

Outbox in `delivery` → relay → exchange `swiftdrop.events` (topic, routing key
`parcel.status-changed`) → quorum queues `notification.parcel-status-changed`,
`merchant.parcel-status-changed` with DLX `swiftdrop.dead-letter` and `<queue>.dlq`. Consumers
deduplicate, order by sequence, hold gaps pending and reconcile via `ParcelEvents`. Notifications:
mock SMS for customer parcels on `PICKED_UP`, `OUT_FOR_DELIVERY`, `DELIVERED`, `FAILED`. Webhooks:
delivery records, signed, SSRF-checked, retried, merchant-isolated. Tuning values: ADR 0004 §9.

**Proposed (D-29):** the dedupe/sequence/pending/reconcile algorithm is written once as a technical
helper in `shared.messaging` (no business types; each module supplies its own repositories), so
`notification` and `merchant` do not duplicate it (IMP-6).

### 8.6 Live tracking

`tracking` keeps `SseEmitter`s per tracking number in memory, sends the snapshot from
`ParcelQueries.byTrackingNumber` on connect, and pushes status events received in-process after
commit. No persistence. A missed push is repaired by reconnect (snapshot). Proposed: public stream
only (**D-14**), timeout 30 min, heartbeat 25 s, max connections per tracking number configurable.
